## Dependencies and risks

- **Package A depends on the window contract.** It is built and tested, so the new member can start in week 1 with the demo, which writes windows. Contract changes after week 1 cost both sides.
- **The migration and the edge restart go together.** After `--apply`, an edge node still on the old code loses its class within a minute, because it looks for `camera_configs.class_id`. Camera AI on the new code reads nothing from Firestore: restart it and save each camera on the camera page in the same sitting.
- **The `Web` branch keeps moving.** Merge `camera-ai` into `Web` in week 1, before the web team builds more on its old camera page.
- **The scoring constants are unvalidated starting values.** Package D gives the report its evaluation section. Without consented data there is no number to report, so the consent form must leave the mentor in week 2.
- **Free plan quota.** The quota ran out on 1 November. Since 4 November the edge node writes nothing to Firestore, and a lesson costs about 65 writes. The largest remaining cost is the report job's reads (`docs/web_admin_integration.md`, Still open).

## Package A brief (new member)

**Goal.** The web backend computes every concentration number from the edge node's windows (`edge-data/sessions/{s}/windows.jsonl`). The fields are described in `docs/edge_node.md`, "Posture windows", and the allowlist is `camera-ai/src/privacy/session_window.py`.

**Code:**

- `backend/services/scoring_service.py`: pure functions, no Firestore. Port the formula from `camera-ai/src/engagement/engagement_score.py::compute_score_from_durations`: score = 100 × (1 − head_drop share − 0.5 × slumping share). Then compute for each seat:
  - `concentration`: the last 6 windows of the latest `run`;
  - `avg_concentration`: all windows;
  - `observed_sec`: the sum of the three posture times;
  - `status`: `away` when the latest `end_sec` minus `last_seen_sec` is more than 30; `drowsy` when `last_state` is `head_drop`; `distracted` when it is `slumping` or `last_behaviour_sec` is within 5 s of the end; `focused` otherwise;
  - `distraction`: all alerts;
  - `interaction`: `side_conversation` alerts.

  Keep every constant in one place.
- `backend/jobs/scoring_worker.py`: polls every 5 s for new windows and keeps each live session's totals in memory.
  - It writes the session's `result.json` with the existing fields.
  - When a window says `completed` or `incomplete`, it writes the session's `evaluations.json`.
  - It also adds `is_present` (seen for at least 60 s), `attention_score` (`avg_concentration`) and `is_attention` (at least 70) to `sessions/{s}/monitored_students/{seat}`.
  - It is safe to restart: it rebuilds the totals from the stored windows.
  - Until the switch in week 4, it writes to shadow files.
- `backend/services/report_service.py`: when a session has windows but no evaluations, compute them with the scoring service.

**Tests.** They run without credentials, on `camera-ai/tests/fake_firestore.py` and a temporary `edge-data/` like the other backend tests:

- unit tests for the scoring service on hand-made windows;
- a parity test in `backend/tests/test_edge_contract.py`: the edge runtime replays a lesson, and the backend's numbers from its windows match the edge node's own within 1 point, with equal statuses.

The one known difference: `avg_concentration` where a seat was hidden for more than 30 s. The windows' behaviour is the intended one.

**Out of scope.** Edge code, frames, keypoints and the Rules. The worker never reads `seat_map` or student names; the student mapping stays in `monitored_students`.

**Done when:**

- the parity test passes;
- a restarted worker produces the same documents;
- the pilot lessons show no unexplained difference;
- `docs/web_admin_integration.md` describes the worker.
